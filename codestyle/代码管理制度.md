## 0. 三条硬规矩（只记这三条也够用）

1. **`main` 分支不直接改**，所有改动先在自己分支上做，再合进来。
2. **每次提交按类型写**：`feat` 加功能 / `fix` 改 bug / `release` 发版。
3. **提交前自动检查**，红了先改完再提交。跳过检查只能偶尔用（`--no-verify`），事后要补。

> 剩下的都是围绕这三条的细节。看完第 1、2、3 章就能干活了。

## 1. 分支：一共 6 个名字，不用再想

| 分支 | 干什么用 | 从哪拉 | 合到哪 |
|---|---|---|---|
| `main` | **随时能烧机的版本**，只放验证过的东西 | — | — |
| `dev` | 日常攒功能，允许暂时不能烧 | main | main（发版时） |
| `feature/xxx` | 加一个新功能 | dev | dev |
| `fix/xxx` | 改一个 bug | dev | dev |
| `release/v1.2` | 发版前冻结，只修阻塞性问题 | dev | main，并回灌 dev |
| `hotfix/xxx` | 现场出问题、来不及走流程 | main | main，并回灌 dev |

**命名规则**：`前缀/小写单词-小写单词`

```
✅ feature/fpc12-raw    fix/uart-ore    release/v1.2    hotfix/laser-crash
❌ feature0_1   新功能   张三   20261105-fix   Feature/FPC12
```

> 分支名写错了也能改：`git branch -m 新名字`（还没推到云效时）。
> 已经推上去了就别改名了，直接新建一个对的。

## 2. 操作流程

> 所有命令在**项目根目录**、PowerShell 里执行。
> 注意：这台机器上 `python` 指向的是应用商店占位程序，会报 9009，**要用 `py -3`**。

### 2.1 加一个新功能（feature）

```powershell
git switch dev
git pull                                  # 先同步，别在旧代码上开工
git switch -c feature/功能名

# ---- 改代码、Keil 里编译、上板自测 ----

py -3 codestyle\check_code.py                 # 先手动体检一遍（可选，提交时也会自动跑）
git add -A
git status                                # 看一眼有没有混进奇怪的东西
git commit -m "feat(adc64): 增加 FPC12 原始值读取"
git push -u origin feature/功能名
```

然后到云效上建**合并请求（MR）**：`feature/功能名` → `dev`，填一句"改了什么 + 怎么验证的"，合并。

### 2.2 改一个 bug（fix）

和 2.1 一样，只是换个分支名和类型：

```powershell
git switch dev
git pull
git switch -c fix/问题名
# ---- 只改这一个问题，别顺手重构 ----
git commit -m "fix(uart): 清 ORE 标志，避免连续收包丢字节"
git push -u origin fix/问题名
```

**提交信息里要写"改之前是什么现象"**，否则三个月后没人知道这个 `fix` 修的是啥。

### 2.3 发版（release）

```powershell
# 1) 从 dev 拉发版分支
git switch dev
git pull
git switch -c release/v1.2

# 2) 改版本号（一处改完，另两处要对上）
#    Core\Inc\config.h  →  #define FW_VERSION "1.2"
git add Core/Inc/config.h
git commit -m "chore(release): 版本号改到 1.2"

# 3) 发版前检查（版本号、README 是否一致）
py -3 codestyle\check_code.py --release v1.2

# 4) 编译，把 MDK-ARM\Objects\Severo.hex 另存为 Severo_v1.2.hex

# 5) 合到 main
git switch main
git pull
git merge --no-ff release/v1.2
git push origin main

# 6) 打标签（标签名必须和 FW_VERSION 一致）
git tag -a v1.2 -m "v1.2: 一句话说清这版改了啥"
git push origin v1.2

# 7) 回灌 dev，删发版分支
git switch dev
git merge main
git push origin dev
git branch -d release/v1.2
```

发版要留档的四样东西（放公司网盘一个文件夹里，命名 `v1.2`）：

1. `Severo_v1.2.hex`
2. 这一版的**接线/引脚表**（改了引脚之后，旧表就再也对不上了）
3. 标定参数（阈值、死区、集中度门限）
4. 一页变更说明

### 2.4 现场救火（hotfix）

```powershell
git switch main
git pull
git switch -c hotfix/问题名
# ---- 最小改动，只修这一个 ----
git commit -m "fix(cmd): 现场断光时状态机死锁"
git push -u origin hotfix/问题名
# 合到 main → 发版 v1.2.1 → 别忘了回灌 dev
git switch dev && git merge main && git push origin dev
```

## 3. 提交信息：只有一个格式

```
类型(模块): 说明
```

- **类型必须是下面这几个之一**，小写
- `(模块)` 可省，写目录名或文件名里的小写单词最好（`adc64` `uart` `cmd` `ui`）
- 说明用中文可以，**首行不超过 50 字，不加句号**
- 首行下面可以空一行写详细原因（可选）

| 类型 | 什么时候用 | 例子 |
|---|---|---|
| `feat` | 加功能 | `feat(adc64): 增加 FPC12 单板原始值读取` |
| `fix` | 改 bug | `fix(uart): 清 ORE 标志，避免连续收包丢字节` |
| `release` | 发版提交 | `release: v1.0 四条边采集稳定` |
| `hotfix` | 现场紧急修复 | `hotfix(cmd): 断光死锁` |
| `docs` | 只改文档 | `docs: 补 PCB 物理顺序对照表` |
| `test` | 只改测试/临时验证 | `test(fpc12): 新增原始值测试工程` |
| `chore` | 杂项（.gitignore、版本号、清理） | `chore: 忽略 dist 和安装包` |
| `hw` | 改了引脚/硬件常数 | `hw(config): EN3/EN4 改到 PH11/PH10` |
| `refactor` / `perf` / `build` / `revert` | 重构 / 性能 / 编译配置 / 回滚 | 按需 |

**好 / 坏对照**

| ✅ 好 | ❌ 会被自动检查拦下 |
|---|---|
| `fix(adc64): CS 拉高后补 50us，消除相邻通道串扰` | `update` |
| `feat(ui): screen_ui 支持 43 点 PCB 顺序` | `修改` |
| `hw(config): ADC64_A_CS 从 PE3 改 PI8（飞线实测）` | `改好了` |
| `chore: 移除 dist 目录` | `feat: 更新` |

**一次提交只做一件事**。顺手改的格式要单独提交，否则以后回滚会连累正常改动。

## 4. 什么东西绝对不能传上去

| 类别 | 例子 | 说明 |
|---|---|---|
| 编译产物 | `MDK-ARM/Objects/`、`*.o` `*.axf` `*.map` | 编一次就生成，传上去只会越来越大 |
| 打包输出 | `dist/` `build/` | 同理，几百个文件 |
| 安装包 | `_pkg/*.exe`、`*.msi`、`*.zip` | 放网盘，要用时从网盘拿 |
| J-Link / Keil 本地文件 | `JLinkLog.txt`、`JLinkSettings.ini`、`*.uvguix.*` | 每台机器都不一样，传了会互相覆盖 |
| Office 锁文件 | `~$xxx.pptx` | 打开文档时才生成，关掉就没了 |
| 密码 / 私钥 | WiFi 密码、token、`*.pem` | 一旦传上去就等于泄露，改密码 + 清历史 |

这些规则已经写进 `.gitignore` 了，正常情况下 `git add -A` 会自动跳过。
**拿不准的时候跑一句**：

```powershell
py -3 codestyle\check_code.py
```

## 5. 自动检查（已经做好了，装一次即可）

### 5.1 装

```powershell
powershell -ExecutionPolicy Bypass -File codestyle\install_hooks.ps1
```

一台电脑装一次，之后每次 `git commit` 自动跑。

### 5.2 每次提交自动查 6 项

| # | 查什么 | 拦不拦 |
|---|---|---|
| 1 | 有没有把编译产物 / dist / 安装包 / 锁文件 / J-Link 日志传上去 | **拦** |
| 2 | 单个文件是否超过 20MB | **拦** |
| 3 | 有没有明文密码、私钥 | **拦** |
| 4 | 新增的 `.c` `.h` 有没有忘记加进 Keil 工程（`*.uvprojx`） | 提醒 |
| 5 | 中断服务程序里有没有调用 `board_delay_ms/us` | **拦** |
| 6 | 提交信息格式对不对 | **拦** |

> 第 4 项特别值钱：新文件忘了加进 Keil 工程，自己电脑能编，别人拉下来直接报错。

### 5.3 报错怎么办

| 屏幕上的报错 | 你该做什么 |
|---|---|
| `Keil 编译产物 × 24` 之类 | 这些文件本来就不该传：`git rm -r --cached MDK-ARM/Objects` |
| `打包/构建输出目录 × 939` | `git rm -r --cached dist` |
| `大文件（>20MB）` | 从仓库里撤掉，放网盘 |
| `提交信息格式` | 按第 3 章改：`feat(模块): 说明` |
| `提交类型不在白名单` | 类型只能是第 3 章表格里那几个 |
| `源文件没加进 Keil 工程` | Keil 里右键 Group → Add Existing Files |
| `中断里调用了延时` | 把逻辑挪到主循环，中断里只置标志位 |

> `git rm -r --cached 目录` 只是**取消跟踪**，本地文件还在，不会删东西。

### 5.4 临时跳过

```powershell
git commit --no-verify -m "feat(x): 说明"     # 偶尔用，事后记得回头补
git config --unset core.hooksPath              # 彻底关掉（不建议）
```

## 6. 怎么保证"每个人上传都过检查"（服务端强制）

### 6.1 先说清楚：本地钩子拦不住"不装"和"故意跳过"

| | 本地钩子（第 5 章） | 服务端门禁（本章） |
|---|---|---|
| 在哪里跑 | 开发人员自己的电脑 | 云效上，**推上去之后** |
| 防的是什么 | 手滑、忘了 | 绕过、没装、新人 |
| 能不能跳过 | 能：`--no-verify`、卸载钩子 | **不能** |
| 效果 | 秒级反馈，少返工 | 不通过就**合不进 main** |

所以"上传必须经过检查" = **保护分支 + 合并请求 + 流水线门禁**，三个一起开。
本地钩子只是让你提前发现，不是关卡。

### 6.2 配一次，大约 15 分钟

**第 1 步：把 `main` 设成保护分支（禁止直接 push）**

代码库 → 设置 → 分支设置 → 保护分支 `main`：

- 允许推送：**仅管理员**（或者谁都别给）
- 禁止强制推送、禁止删除：开

> 实际效果：开发人员推不上去，只能提合并请求。**这是所有服务端检查的入口。**

**第 2 步：建一条只做检查的流水线**

云效 → 流水线 → 新建流水线：

| 配置项 | 填什么 |
|---|---|
| 名称 | `code-check` |
| 代码源 | 本项目代码库，默认分支 `dev` |
| 触发方式 | **合并请求触发**（有人提 MR 就跑）+ 手动触发 |
| 阶段任务 | 「执行命令」（Linux 构建机） |
| 命令 | `sh codestyle/ci_check.sh` |

这行脚本干的事：拉基线分支 → 算出本次改了哪些文件 → 跑 `codestyle/check_code.py --ci` →
有编译产物 / 大文件 / 明文密码 / 中断里延时 / 漏加进 Keil 工程，就返回非 0 → **流水线失败**。

> 只跑一个 Python 脚本，几十秒结束，几乎不消耗构建额度。
> 如果日志里出现"构建机上没有 python3"，把构建镜像换成带 Python 的（如 `python:3.11`），
> 否则这道门禁是空的 —— 脚本这时会**判定为不通过**，不会放行。

**第 3 步：把流水线卡在合并请求上**

代码库 → 设置 → 合并请求设置：

- 勾选「合并前必须通过流水线」→ 选 `code-check`
- 至少 1 人评审通过：开

> 从这一刻起：**检查不通过 = 合并按钮点不动 = 进不了 main。**
> 这就是"开发人员上传代码会经过检查"的强制点，本地 `--no-verify` 绕不过去。

**第 4 步（可选）：再加一道 Codeup 代码检测**

代码库 → 代码检测 → 新建检测任务：触发方式「提交触发」，分支 `main`、`dev`，
方案选「敏感信息扫描」（有 C/C++ 规约方案就一起选）。

这层查的是"有没有把口令、密钥写进代码"，和流水线互补。

### 6.3 第一天对齐

```powershell
git clone <仓库地址>                                                # 1. 拉代码
cd severo
powershell -ExecutionPolicy Bypass -File codestyle\install_hooks.ps1    # 2. 装本地钩子
py -3 codestyle\check_code.py                                           # 3. 确认能跑
```

### 6.4 效果对照

| 场景 | 只有本地钩子 | 加上服务端门禁 |
|---|---|---|
| 忘了装钩子，直接推 | 混进去 | MR 跑流水线，红 → 合不进 |
| `git commit --no-verify` 跳过 | 混进去 | 一样红 |
| 传了 900 个 `dist` 文件 | 本地就拦 | 双保险 |
| 谁改动了分支保护设置 | 不知道 | 管理员可在组织后台查 |

## 7. 四件坚持的事

1. **每个月 `git push`。** 只存在本机一个副本的代码，等于没有代码。
2. **每次发版必须打 tag**，并且和 `FW_VERSION` 一致。现场那台机器烧的是哪一版，要能一眼查出来。
3. **大文件不进 git**（网盘 / 制品库）。
4. **改引脚、改串口协议，必须同步改文档**（`docs/` 里的接线表和 README 的版本历史）。

## 附录 B：常用命令速查

| 我想干什么 | 命令 |
|---|---|
| 看当前状态 | `git status` |
| 看改了哪些内容 | `git diff` |
| 看提交历史 | `git log --oneline -10` |

| 打标签 | `git tag -a v1.2 -m "说明"; git push origin v1.2` |
| 看有哪些标签 | `git tag` |
| 回到某个版本看看 | `git switch --detach v1.2` |

## 附录 C：出问题找谁

| 现象 | 先干什么 |
|---|---|
| 提交被拦下 | 看屏幕上的"怎么改"，按第 5.3 节处理 |
| 钩子没反应 | `git config core.hooksPath` 应该是 `codestyle/hooks`；没有就重跑 `codestyle\install_hooks.ps1` |
| **合并请求的"合并"点不动** | **流水线 `code-check` 没通过（第 6 章）**：点进流水线看日志，红在哪一项就改哪一项 |
| 流水线日志说"没有 python3" | 把构建镜像换成带 Python 的（如 `python:3.11`），否则门禁是空的 |
| `python` 报 9009 | 这台机器要用 `py -3`（或 `py -3 codestyle\check_code.py`） |
| 推送被拒 | 通常是远端有新提交，先 `git pull` 再推；或者你推的是受保护的 `main` |
| 设备在现场、代码没提交 | 先本地提交，回公司立刻 push，提交信息注明"现场补录" |
